# Archify Reader

这是独立的配套 skill，使用本地 Node.js（建议 22 或更新版本）。原生图由官方 Archify 生成；本包只增强阅读，不修改官方 skill、schema 或渲染器。

## 流程

1. 若尚无原生图，找到用户现有的 Archify skill，按其说明生成并检查 HTML。不擅自安装或更新它。
2. 与用户确认或复用业务 MD，给图中的稳定节点 ID 关联一句短注释和一段详情。详情与注释必须按下方《详情内容规范》为"看过图、没看过代码"的读者重写，不得把业务 MD 段落原样搬进面板。更新图时保留语义未改变的 ID。
3. 在输出目录写 `reader.json`，执行本 skill 的 `scripts/build.mjs`，传入该 JSON 的路径。
   **描述已有实现时必须先读** [references/code-evidence.md](references/code-evidence.md)，默认交付源码对照，不等待用户说“证据模式”。AI 阅读固定版本源码、撰写 MD 并声明章节与源码位置；构建器只检查格式、关联和来源，不推断业务。
   写节点间的承接与引用时，读 [references/node-references.md](references/node-references.md)，在 MD 中就地解释并引用目标节点，在 JSON 中声明关系。
4. 详情入口位于图右下角的原生工具栏，按钮显示“详情”，选中节点后打开对应章节。打开增强 HTML，检查节点注释、详情对应、关闭后聚焦/缩放保留，以及原生搜索与主题切换。构建收据只证明静态关联检查，不证明浏览器交互或业务事实。

```json
{
  "version": 1,
  "input": "../original/diagram.html",
  "output": "diagram.reader.html",
  "codeSource": { "repository": "../../my-project", "commit": "填写查证过的完整小写commit哈希" },
  "nodes": [
    {
      "id": "save_working",
      "label": "保存工作态",
      "document": "details.md",
      "heading": "保存工作态",
      "note": "保存当前编辑内容，尚未归档。",
      "evidence": [{ "heading": "保存当前编辑内容", "snippets": [{ "file": "src/save.js", "startLine": 1, "endLine": 8 }] }]
    }
  ]
}
```

```text
node <本skill目录>/scripts/build.mjs <输出目录>/reader.json
```

示例中的仓库、commit、文件、行号和 MD 子标题须替换为实际查证值，不能直接当作证据。

## 证据交付规则与原地升级

- 现状梳理、旧项目分析、重构前基线都默认提供证据。讨论稿、结论待确认、即将重构、节省成本、另一个 MD 有 file:line、AI 已经读过代码，均不是省略理由。固定旧版本是现状依据，重构后仍可回看。
- 每个已配置详情的节点必须有 `evidence`；只有整节点为未实现设计，或用户明确要求省略，才可用 `evidenceExemption` 写明类型与原因。格式见源码对照说明；原因会显示在页面和收据里。不要每次询问模式，也不能冒称用户要求。
- 同节点混有现状与提案：为现状执行步骤配置证据；未实现内容单独标为“拟议，尚未实现”，不能借设计内容豁免整个节点。关键条件、失败分支、前后承接也应有充分依据，不用一处片段冒充整节点覆盖。
- 无法访问源码、没有可用 commit、正文来自未提交改动时，报告具体缺口并请求解决来源或范围问题；不能把已有实现改称设计，也不能偷偷选普通模式。不得自行提交业务源码来凑版本。
- 用户要求给已有增强版加证据时，**原地补充，不重画**：读取现有 manifest、MD、原生 HTML 与收据；保留原图、节点 ID、关系引用、输入输出路径和已正确的叙述；补 `codeSource`、各节点 `evidence`，必要时把原有步骤分为第一层子标题。输入仍用原生 HTML，重建同一个增强 HTML。
- 查证中发现原文错误，列出证据及修正原因，不能为保留原文而配假证据，也不擅自改动业务要求。完成后检查原图未变、节点引用仍可用、页面能就地看源码，报告证据节点、豁免节点及未解决事项。
- 生成内容只修改产物的 MD/JSON，通过构建脚本生成 HTML；不得修改 skill 工具代码、放宽检查来完成交付。

## 详情内容规范（2026-09-05 作者裁决加入）

读者设定：**看过业务图、没看过代码的业务裁决者**。本规范来自一次真实外部使用的失败——陌生 AI 按旧说明把业务 MD 段落原样搬进详情，满篇代码标识符，作者无法阅读。

1. 正文按真实执行顺序讲"先做了什么、后做了什么"，一步一句事实。**顺序本身就是检验点**：逻辑不对，读者要能看出来。
2. **业务叙述零代码标识符**（变量、函数、表名、配置名、状态码、HTTP 方法不放进白话正文）。源码对照模式在左侧保留真实代码及路径、行号，右侧仍只讲业务；普通模式可用“想核对的话”指向业务文档。2026-09-05 后续裁定由“全页零标识符”改为叙述与证据分层。
3. 用业务词说事：谁、对什么数据、做了什么动作、得到什么结果。必要术语第一次出现给一句白话注释。
4. 失败分支也是事实：这一步出错会怎样、影响谁；禁止只写成功路径。
5. 普通模式沿用：一句话职责 / 按先后做了什么 / 什么会出错 / 想核对的话。源码对照模式将执行步骤拆成可配对的子标题，保留范围说明和未验证的失败后果。
6. 客观白描：不修饰、不科普、不“专业腔”总结。涉及实现现状的顺序、条件和结果应核对源码；业务 MD 与源码冲突时记录差异，不替用户改变业务要求。不把没跑过的失败情景写成已验证事实。
7. **首尾承接**：开头说明从哪个节点接过什么、前面完成了什么；结尾说明本次执行在哪里结束、留下什么结果，以及谁在什么条件下进入哪个节点。入口/终点或独立节点如实说明，不为填格式虚构上下游。
8. **依赖就地解释**：不要只说“现有规则”“前面处理过”。先写当前判断所必需的一句话规则或数据来源，再引用对应节点；区分“配置在哪里设置”和“判断在哪里执行”。有多个分支时明确列出条件，链接不替代解释。
9. **顺序来自执行而非排版**：正文沿当前调用链讲，遇到函数调用在当前位置解释其必要行为，再返回主线。条件、并行、异步触发需明示；配置依赖、数据供后续读取不等于紧接着执行。按源码校验顺序是 AI 的责任，构建器仅保持 MD 顺序，不证明它符合源码。

悬停注释同样守第 2、3 条：一句业务事实，不放标识符。

借口对照（写详情时自查）：

| 借口 | 实情 |
|---|---|
| "业务文档里就是这么写的" | 文档可以密，详情必须重写 |
| "带变量名更精确" | 白话负责让人理解业务；源码及代码位置放在证据层，分层不等于删掉核对依据 |
| "读者应该懂技术" | 读者设定见本节第一句，不许擅自更换 |

本包附带虚构校园报名示例。内容规范用于生成可核对的业务说明，仍需读者裁决业务含义。

## 第一版边界

- 路径相对 `reader.json`；MD 必须在其目录内。`heading` 精确匹配唯一 Markdown 标题，详情包括它的子标题，直到下一个同级或更高级标题。重命名标题后重新构建会检查关联。
- 输出 HTML 在关联文件同目录，详情嵌入，可离线双击。修改 MD 或注释后重新构建，不手改生成 HTML。
- 源码对照默认必需：构建时需要 Git 与本地源码仓库，阅读 HTML 不需要它们。源码来自固定 commit，不反映未提交改动；修改版本后重新核对映射。显式豁免节点使用普通详情并显示原因。旧的无证据 JSON 重新构建时会报缺失；已生成的历史 HTML 不受影响。
- 支持整节点悬停注释、键盘提示，以及声明过的节点引用：在当前详情面板切换目标，并可返回上一详情及阅读位置。未支持任意词语或连线注释。普通外链/本地文件链接仍只显示名称与地址，不执行；原始 HTML 作为文字呈现。
- 不额外扫描或重写业务事实。详情不足时向用户说明，不从节点名称编造规则。未关联的图节点在构建收据中报告，在页面中显示暂无详情。
- 输入必须为未增强的原生 Archify HTML。保留原生文件与收据，衍生 HTML 使用自己的 `.receipt.json`。适配标记缺失时报告兼容问题，不修改上游来强行通过。
- 本包以本地 Archify `2.17.0-dev.1` 样张验证。内部 DOM 并非正式插件 API，升级后用真实样张复验交互。

核心代码：`scripts/build.mjs` 装配与检查，`scripts/evidence.mjs` 读取源码快照并配对，`assets/reader.js` 页面交互（适配逻辑集中在顶部），`assets/reader.css` 独立样式。Markdown 解析使用附带 MIT 许可的 marked 17.0.5；原包无需运行时安装依赖。

本文件可以直接交给 AI 读取；当前存放在项目 `skills/` 中，未自动安装到各 AI 工具的 skill 发现目录。
