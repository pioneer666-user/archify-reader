# 节点承接与引用

读者从图进入任一节点后，应能理解它从哪里接过什么、在这里按何种顺序处理、结果供谁使用。AI 阅读源码并填写这些内容；构建器只检查引用是否合法，不核实真实执行关系，也不强迫旧文档补虚假的上下游。

## 声明方法

节点的 `references` 为可选数组，每项只含 `target` 与 `relation`。目标使用图中的稳定节点 ID，并必须在同一 manifest 中配置可构建的详情。正文用标准内联 Markdown 链接 `[目标节点名称](node:目标ID)`；名称必须与目标节点的 `label` 完全一致。

例如，以下片段放在“落库提交”节点内（目标节点还需按普通格式配置）：

```json
"references": [
  { "target": "validate_submit", "relation": "input" },
  { "target": "config", "relation": "configuration" },
  { "target": "view_data", "relation": "later" }
]
```

```markdown
### 从哪里接过来
承接[校验与门禁](node:validate_submit)：答卷通过提交检查后，进入保存阶段。

### 保存前判断
读取[采集配置](node:config)中的“提交后锁定”开关，按数据归属人的身份判断本条答卷是否锁定。
此处继续写清实际条件和分支，不能用链接替代规则说明。

### 结束与后续
本次提交在返回结果处结束。有权限的管理者发起[查看与统计](node:view_data)时，再读取保存的数据。
这不是提交接口自动执行的下一步。
```

以上是语法示例；生成新项目文档时必须核对实际源码，不能照抄其中的业务结论。

| relation | 读者含义 | 写作要求 |
|---|---|---|
| input | 前置输入 | 来源节点已完成什么，交来什么 |
| configuration | 配置来源 | 具体设置是什么，在哪里使用 |
| dependency | 依赖 | 当前步骤使用了对方的什么能力/数据 |
| next | 继续执行 | 当前处理完成后，由什么条件触发继续调用；异步时明说 |
| later | 后续操作 | 当前执行已结束，之后由谁另行发起什么 |

同一目标每个节点声明一次，可在正文多次引用；本版一对节点只声明一种主要关系。如果同一目标有多种关系，在正文说明差别，不用重复项伪装成已支持多重关系。引用自身、重复项、未知关系、未声明链接、名称不匹配、声明未使用都会使构建失败。代码块和行内代码中的链接示例不会变为按钮。

## 阅读行为与校验边界

- 引用在文字所在位置显示为带下划线的节点名；悬停或键盘读屏可获知关系类型。点击后在同一面板打开目标详情。
- “返回上一详情”恢复来源段落的滚动位置和引用按钮焦点；从下拉框主动换节点或重新打开面板会清空这段阅读历史。
- 详情间跳转不改变底层图的聚焦与缩放，关闭面板回到原图。点击引用表示读者导航，不表示程序实际执行了这个节点。
- 构建收据记录声明的关系和实际引用次数，仅证明目标与名称合法；它不验证原图是否有相应连线，也不证明箭头等于调用，更不验证 MD 的执行顺序正确。

## 给陌生 AI 复跑时

提供待分析的源码仓库、链路范围、官方 Archify 与本 reader skill；让它自行阅读源码和生成 MD、图规格、关联 JSON。生成内容时不修改工具代码或放宽检查；遇到事实不明就报告缺口。

验收时从链路中间任选一个节点，检查开头的输入、局部规则、条件分支、执行结束点和后续触发者。再点引用核对目标，确认退出后能回到原位置。若 AI 只模仿了格式、仍用含糊规则或把后续操作写成自动调用，记录为内容失败，即使构建全绿也不算这一轮目标通过。
