# 源码与白话对照 · 第一版

AI 负责阅读源码、编写白话和声明对应关系；构建器负责合法性及来源校验，不自动解释代码。
生成内容时修改 MD 和 JSON，工具实现的修改应作为独立维护任务，不能为通过构建而放宽检查。

## 输入约定

仍用 `version: 1`，在原 manifest 顶层加 `codeSource`，每个描述已有实现的详情节点加 `evidence`。
这是默认交付要求，重构前的讨论稿也适用。下面是字段示例，commit 和行号必须换为实际查证的值：

```json
{
  "version": 1,
  "input": "diagram.html",
  "output": "diagram.evidence.html",
  "codeSource": {
    "repository": "../../my-project",
    "commit": "填写已核实的完整小写commit哈希"
  },
  "nodes": [{
    "id": "save_submission",
    "label": "落库提交",
    "note": "答卷保存后，继续更新日志与待办。",
    "document": "details.md",
    "heading": "落库提交",
    "evidence": [{
      "heading": "保存答卷",
      "snippets": [{
        "file": "backend/submit.py",
        "startLine": 25,
        "endLine": 36
      }]
    }]
  }]
}
```

对应 MD：

```markdown
## 落库提交
本节从校验完成后开始。

### 保存答卷
把答卷写入数据库。等待保存完成后，才继续下一步。

### 待核实
中途失败时的回滚结果尚未做运行验证。
```

- `repository` 是本地 Git 仓库根目录，可用相对 manifest 的路径或本机绝对路径。HTML 中只显示目录名和 commit；换电脑构建时需调整本地仓库位置，已有 HTML 可直接离线读。
- `commit` 必须是实际存在的完整 commit 哈希（40 或 64 位小写十六进制）。先确定版本，再读该版本写文档，不能按工作区内容写完后随便附一个 commit。第一版不读未提交源码，不做自动更新。
- `file` 用仓库根目录内相对路径、正斜杠；只接受 commit 中的普通 UTF-8 文本文件，不跟随符号链接。
- 行号从 1 开始，首尾均包含；一段白话可对应多个文件中的片段。JSON 不允许手填 `code` 正文。
- `evidence.heading` 必须唯一匹配该节点详情内的第一层子标题，正文不可为空。不把嵌套子节另行重复配对。最终顺序取自 MD，不取自 JSON。
- 未关联段落原样保留，用于说明范围、上下文和待核实事项。页面会区分有源码连线的段落，但不证明未关联内容完整，也不替 AI 检查遗漏。

## 编写分寸

整节点没有实现代码（纯设计），可用 `"evidenceExemption": { "kind": "design", "reason": "此节点是拟议功能，尚未实现。" }` 替代 evidence。
只有用户明确要求省略源码时，才可用 `kind: "user-requested"`，reason 记录具体要求与范围。不能由 AI 为省事自行选择；构建器只能检查声明格式，无法验证用户是否真的授权。
豁免与 evidence 不能同时出现在一个节点，原因会转义为文字显示在详情里，并记录到收据。全部节点豁免时不配置 codeSource。缺代码但声称描述实现的节点应报告阻碍，不能冒用设计豁免。
混合节点仍配 evidence：现状步骤逐段对照，提案明确标为未实现；范围或待核实段落可以不配对。构建器检查节点是否配置证据，不证明段落覆盖完整或业务解释正确。

以一块业务逻辑为单位，保留支持该叙述所需的条件和失败分支。必要时同时引用调用处和被调用函数，不能用一行函数名冒充其内部行为的证明。单行调用可以作为完整函数块的补充。

正文讲谁对什么做了什么、先后和结果；变量名、路径和行号只在源码区展示。
节点开头承接上游输入，末尾区分本次执行结束与后续触发；正文中的配置/规则来源就地解释并引用节点，语法见 [node-references.md](node-references.md)。源码对照的每段仍按当前执行顺序排列，不能按来源文件位置或 JSON 数组顺序重新组织业务。
已有业务文档若概括错了，核对后在实验记录中说明修正理由，不静默改写正式要求。
局部片段不能证明整个系统没有事务、没有权限检查，也不能证明业务运行成功。

## 构建与检查

命令仍是 `node <skill目录>/scripts/build.mjs <manifest路径>`。

构建会检查每个已配置详情节点是否有证据或显式豁免，以及 commit、文件类型、行范围、节点和章节关联；失败时不替换上一份 HTML 或收据。图中未配置详情的节点仍以警告报告，不算已覆盖。
收据 `evidenceCoverage` 列出有证据的节点与豁免原因，并将段落覆盖及豁免理由真实性标为未验证。
页面代码块来自 Git 对象，按文字转义，不执行；收据保存来源文件、Git blob 和 SHA-256，以及每组对应关系。
`semanticVerification` / `runtimeVerification` 保持 `not_run`，表示构建器没有验证解释正确性或实际业务运行。
固定版本内的行号不漂移；改 commit 后即使行号仍合法，也必须由 AI 重新核对语义，合法性检查不能发现全部错配。

验证桌面两栏、窄屏逐组堆叠、代码可完整滚动阅读，以及普通/证据节点切换、关闭详情返回图、原生搜索和主题。不得通过缩小原图或全局 body 留白来腾位置。
